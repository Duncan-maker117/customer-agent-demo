# 企业落地评估与改造路线

评估日期：2026-10-22。范围：当前工作树的静态代码、Git 差异和已有运行记录；本次未调用模型、连接店铺、发送消息或重新执行测试套件。

## 当前结论

项目具备向单店客服辅助工具发展的技术基础，但当前证据尚不支持“已在企业生产环境落地”。已记录的运行验证是桌面启动和五类离线知识匹配场景；真实模型与真实平台收发仍缺少验证记录。

Windows 桌面应用也能用于实际业务。首个目标建议为“一家店铺、一个客服账号、有限知识范围、人工确认发送”，逐步开放经过验证的低风险自动回复。

“代码已有”不代表已在真实店铺验证。以下条目是静态检查发现的风险和建议，不是已经复现的生产事故。

## 关键代码依据

1. `service/demo_conversation.py` 使用内置虚构资料；调用模型时 `use_tools=False`，与实际平台的 Agent 处理链路分离。验证该页面不能代替平台链路验证。
2. `Message/core/queue.py` 使用 `asyncio.Queue` 和进程内 `set` 去重。进程异常退出后，队列和去重状态无法单靠这些结构恢复。
3. `Channel/pinduoduo/utils/base_request.py` 对连接错误和超时执行重试，`post()` 也使用统一重试器。远端已处理但本地超时的发送需要专门处理；不能直接认定重复请求一定会被平台去重。
4. `Message/handlers/ai_handler.py` 在发送失败后尝试发送备用回复。原消息是否送达不明时，需避免重试和备用回复叠加，并产生可人工处理的待办。
5. `Channel/pinduoduo/message_rules.py` 的角色设计注明“机器人接待期间人工不会介入”。当前主要处理链路未看到完整、持久化的人工接管状态和发送前归属检查；需验证客服插入回复和模型在途任务的竞态。
6. `database/knowledge_service.py` 的主要文本检索使用 jieba 分词、SQL 文本包含条件和创建时间排序。应先建立检索基准，再决定全文检索或混合检索是否有收益。
7. `Agent/CustomerAgent/custom/session_manager.py` 已有消息持久化，`tool_decorator.py` 已从可信上下文注入身份；不应将这些能力重复建设为另一套独立系统。
8. `Channel/pinduoduo/utils/API/send_message.py` 使用商家网页版域名接口及登录会话。长期运行的接口适用性、会话有效期和变更影响必须单独确认；仓库具备请求代码不等于已有稳定的官方服务接入保障。

## 推荐实施顺序

### 第一阶段：跑通受控业务链路

范围：商品咨询、物流政策、售后规则；赔偿承诺、退款执行、修改订单等操作由人工处理。

流程：接收问题 → 检索店铺知识 → 真实模型生成草稿 → 人工核对和确认 → 发送 → 核对平台结果。

验收证据：

- 记录模型与知识版本、问题、引用来源、生成草稿、人工修改、发送结果及时间；保存脱敏样例。
- 证实平台消息到达正确客户；记录失败或结果未知，不能只凭界面显示成功。
- 验证超时、API 无效、无知识、人工不可用、断网及重登；人工能够立即暂停自动处理。

外部条件：有效模型配置、有权使用的店铺或真实客服工作环境。若暂时没有平台账号，可先由实际客服粘贴问题并确认建议回复；这属于客服辅助工具试用，不能据此宣称拼多多自动收发已落地。

### 第二阶段：补消息可靠性与人工接管

沿用现有 SQLAlchemy + SQLite，按实际模型设计增量表或字段；先在临时数据库验证，不迁移真实业务数据。

- 入站记录：平台、店铺、平台消息 ID、接收时间、处理状态；复合唯一约束防止已接收消息重复处理。
- 发送记录：回复草稿、审批人、发送尝试、平台请求及返回标识、成功/失败/结果未知；对结果未知先核对，不能承诺跨平台“绝对只发送一次”。
- 会话归属：自动处理、等待人工、人工处理中、已结束；生成前及发送前检查归属，接管时抑制尚未发送的模型结果。
- 故障恢复：重启后可查看未完成消息；发送失败有人工待办；记录每次状态变化，避免将日志文件当成业务状态源。

验收证据：重复投递不重复处理；重启后未完成任务可恢复；人工接管后无机器人抢答；未知发送状态可人工核对和处置。

### 第三阶段：建立效果评测与运行记录

建议先整理 100—200 条有标准答案或处理要求的脱敏问题，覆盖商品咨询、同义问法、多轮指代、售后边界、缺少知识、提示注入及不同店铺资料隔离。这个规模是首轮建议，不是行业验收标准。

- 检索：是否找回正确资料，是否引用了过期或其他店铺资料。
- 回复：事实正确率、人工可用率、需修改比例、无依据承诺及应转人工案例的漏判。
- 运行：端到端时延的中位数/P95、模型失败率、平台发送成功/失败/未知比例、每次会话的调用量和成本。
- 业务：在相同问题范围内，对比人工独立处理和使用辅助工具时的耗时、修改量；同时统计失败案例。

先明确指标分母、问题范围和验收目标，再运行评测；不将模型自报置信度当成可以自动发送的唯一依据。

建议从一个店铺连续试运行 5—7 个工作日开始，实际时长由消息量和风险决定。完成备份恢复与停用回退演练后，再决定是否开放低风险自动发送。试运行数据不足时延长观察。

## 首版应控制的范围

优先完成以上三阶段；暂不因“企业级”标签引入微服务、多 Agent、多渠道或大规模集群。SQLite 适合当前单机部署；只有多坐席集中访问、多实例并发等需求出现后，再评估服务端数据库和权限体系。

若扩展为多人协作或多商家服务，需另外设计登录与权限、租户隔离、集中知识管理、审计、部署和数据保留策略；不能将单店试运行外推成多租户平台成熟度。
